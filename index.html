Key Governance Rules

Project Tiering
Lite (<$5K / <40h): 3-stage fast track, IT RGC approval only.
Standard ($5K–$50K): Full 9 stages + all PTX gates, ITC approval.
Major (>$50K / org-wide): Full process + BAPS Inc. Leadership co-approval.
Decision SLAs
ITC meets bi-weekly. Gate decisions: Lite ≤5 days, Standard ≤10 days, Major ≤15 days. Emergency path: ≤48 hours. SLA clock starts on complete submission.
Every Gate: Go / Kill / Hold / Recycle
Every PTX gate and every Stage Gate produces a written Gate Decision Record. Kill and Hold decisions are governance successes — tracked and used in annual policy review.
Change Control
Cost >10% of last approved baseline → ITC notification. >20% → gate re-review. Schedule slip >4 weeks → CR required. All tracked cumulatively.
Emergency Fast Path
Festival/event deadline ≤30 days + Tier 1/2 scope + pre-documented risks → Gates 1–4 combined into a single 48-hour review. Rollout + Closure gates still required.
Benefits Realization
60-day post go-live review comparing actual vs. promised KPIs. Required for Gate 4.5 (Permit to Close). Lessons fed back into process improvement annually.

What is the Stage Gate Process?

A structured sequence of stages and decision points that every IT project must pass through — from the initial idea to production closure. Each gate is a formal review where evidence is assessed and a Go / Kill / Hold / Recycle decision is made. No stage can begin until the previous gate has formally passed.

Exit Point A

Before Stage 1

Department has its own capable team. They self-manage the project but must still follow central governance: security policies and architecture standards.

Exit Point B

After Stage 3 — Requirements done

BAPS BAs help the department define requirements, then the department exits to issue an RFP to an external vendor for the build phase.

Exit Point C

After Stage 5 — Estimate done

IT's estimate exceeds the department's timeline or budget. The department finds an external solution. IT is never pressured to rush and compromise quality.

BAPS Extensions Beyond Cooper

BRD / FRD Split
Cooper treats requirements as one stage. BAPS splits BRD (what/why) from FRD (how) with a formal gate between them — preventing design from starting on incomplete logic.
Exit Points A / B / C
Cooper assumes IT always builds. BAPS provides three structured off-ramps that give departments flexibility while preventing IT burnout from unrealistic expectations.
Readiness Overlap Model
Cooper gates are sequential. BAPS stages overlap: prerequisites for the next stage begin while the current stage is running, preventing stalls (e.g., finding a Solution Architect before Stage 3 ends).
Volunteer RACI
Cooper assumes dedicated staff. BAPS RACI accounts for limited volunteer availability, rotating team members, and the need to distribute accountability across a semi-professional governance structure.
Formal Closure Stage
Cooper's model ends at Launch. BAPS adds Project Closure with formal documentation archival, access revocation, and a Lessons Learned loop that feeds back into process improvements.
Defect Severity Classification
Cooper focuses on business gates. BAPS adds a P0–P3 defect severity framework to formalize what must be resolved before UAT sign-off, preventing "go-live with known issues" disputes.

⚠ Critical Gaps — Must Address Before Process Goes Live

CRITICAL
SG-C1 · No project size tiering — same 8 stages for every request
Current: A 2-hour config change and a 12-month platform both run the full 8-stage process including ITC gate. Industry (Cooper Lite / COBIT risk-tiering): Projects under defined cost/effort thresholds use a compressed 3-stage path (Propose → Build → Close) with IT-level approval only.
Fix: Add Lite path (<40h / <$5K): 3 stages, IT RGC approval, no ITC gate. Standard path: full 8 stages. Major path (>$50K / org-wide): 8 stages + BAPS Inc. leadership co-approval at Gate 1.
CRITICAL
SG-C2 · No benefits realization loop from Closure back to ITC
Current: Stage 9 closes the project, but the Lessons Learned output has no defined recipient, format, or feedback mechanism. Original Gap #28 flagged this but the fix stops at "lessons never loop back." COBIT BAI11 Gate E: Closure must include a formal benefits realization report comparing actual vs. expected outcomes, filed with ITC and used as input for future estimates.
Fix: Add a 60-day post-go-live Benefits Review: actual vs. expected KPIs, lessons filed with IT PM office, ITC sign-off required to formally close the project record.
CRITICAL
SG-C3 · No defined emergency / event-driven fast path
Current: The process has no compressed path for festival-driven or compliance-driven deadlines. Urgent projects either skip stages informally or block on the full process. Industry: Every mature SDLC framework includes a defined expedited track with explicit eligibility criteria, reduced gate count, named approvers, and a mandatory post-event retrospective.
Fix: Add Emergency Track: eligibility (event <30 days, Tier 1/2 scope, pre-documented top 3 risks), Gates 1–4 combined into a single emergency review, 48-hour decision by ITC Chair + IT RGC, Gates 7–9 still required. >3 uses/year triggers process audit.
CRITICAL
SG-C4 · No ITC charter — composition, quorum, and conflict of interest undefined
Current: ITC is referenced as the primary approver throughout but its composition, quorum, voting rules, delegation, and conflict-of-interest handling are never defined. Industry: Every governance framework (COBIT, ISO 38500) requires a defined charter for any committee holding approval authority.
Fix: Add ITC Charter appendix: composition (ITC Chair + IT Director + IT RGC Lead + 2 rotating Dept Lead reps), quorum (3+ members including Chair), voting (simple majority, Chair has casting vote), delegation rules, conflict-of-interest declaration and abstention requirement.
CRITICAL
SG-C5 · Volunteer capacity never modeled in planning gates
Current: Stage 5 (Estimate) and Stage 4 (Technical Design) produce timelines without any mechanism to account for volunteer availability windows, festival blackout periods, or mid-project resource loss. Industry: PMI and PRINCE2 both require a Resource Management Plan at the planning gate — this gap is especially acute for a volunteer organization.
Fix: Add to Stage 5: Volunteer Capacity Plan — maps each resource against their confirmed available hours per sprint, flags festival/event blackout periods, and defines what happens if a key resource becomes unavailable mid-build (PM notifies ITC within 5 days, revised resource plan submitted).

1. Purpose▾

As BAPS Swaminarayan Sanstha continues to expand, demand for IT application development, system enhancements, automation, reporting, integrations and digital solutions continues to grow. This policy formalises how that demand is received, evaluated, prioritised, funded, delivered and accepted.

Consistent evaluation — every request assessed against Sanstha-wide capacity, benefit, budget and risk.
Clear approval gates (PTX) — work only proceeds after review and approval at each gate.
Unambiguous roles — decision responsibilities and escalation paths clear for Departments and IT.
Accountable timelines — delays measured and published transparently against all parties.
PTX (Permit to Execute) — formal authorization required to proceed to the next stage of a project. A permit authorizes the project's next stage only; it is not approval of the project as a whole.
2. Scope▾
IN SCOPE
  • New custom IT system requests
  • New phase (major enhancements) of an existing IT system
  • Critical/Urgent enhancement requests
  • Project-scope change requests affecting approved scope, timeline, cost, resources or delivery commitments
  • Vendor-delivered or vendor-hosted solutions (selection, contracting and exit)
OUT OF SCOPE
  • Defects, incidents, service disruptions and outages — remain with IT RGC production support
Where a production issue is later determined to require an enhancement beyond a bug fix, it transfers into this policy at the appropriate gate (see §13 Conflict Resolution).
In-flight projects: Projects not yet in build join at their next natural gate. Projects in build adopt §§11–14 immediately. Projects in UAT or hypercare complete under existing arrangements.

7. Requirement Workshops▾
A requirement workshop is not a brainstorming or discovery session. Departments must form their own position — resolving internal disagreements — before the workshop. Workshop time is for explanation and clarification, not for the Department deciding what it wants.
Scheduling (§7.2)All workshops scheduled as a series at the start of requirements stage. BA circulates agenda [3] days before each session. Department confirms SME attendance [2] days before.
SME Preparation (§7.3)SME arrives able to explain: current-state process, desired future-state, business rules and edge cases, sample forms/data, volumes and peak periods, internal position where options exist, and which items are MVP vs future phase.
Outcomes (§7.4)BA publishes minutes and requirements within [2] days. SME confirms or corrects within [2] days — no response = confirmed. Open questions tracked in requirements log under §11 SLAs.
Unprepared workshop (§7.5)If SME is absent or unprepared such that the session cannot proceed, BA ends and reschedules. Time recorded as Attributable Delay against the Department. Two consecutive occurrences escalated to Department Lead and ITC.

9. Project Execution Method▾

All requirements must be documented, reviewed and formally signed off before development begins. Agile delivery methods may be used but must include controls to prevent unmanaged scope expansion. Any requirement affecting timeline, cost, resources or approved scope must be a formal change request (§14) or deferred to a future phase. Iteration within an agreed requirement is expected; new requirements introduced through iteration are not.

Demonstration sessions (§9.1) — at minimum at the end of each sprint or milestone, with dates set at PTX-3. SME attendance mandatory. SME confirms or lists specific discrepancies within [3] days (no response = confirmed). Deviation from baseline = defect. Something new or different = change request under §14.

⚠ Critical — Most Likely to Break the Process

GAP A No size tiering

A small project and an org-wide platform both go through four gates with ITC review at each. Departments will route around it. The policy will be seen as too heavy for small work and will be quietly ignored for anything that feels minor.

Recommendation: Implement a 2–3 tier model: Lite (single combined gate, IT-approved, below a cost/effort threshold), Standard (full 4-gate PTX), and Major (full PTX + BAPS Inc. leadership co-approval).
GAP B ITC has no decision SLA

Departments have obligations at every gate; ITC has none. Without a committed turnaround time, "the policy is slowing us down" becomes the standing complaint — and it would be valid.

Recommendation: Define ITC meeting cadence, a decision turnaround (e.g. within one ITC cycle of a complete submission), and an auto-escalation if a decision slips past the SLA.
GAP N Volunteer resourcing not acknowledged

The policy assumes assignable IT resources with predictable capacity. In practice a significant share of delivery capacity is likely volunteer. Nothing covers what happens when a resource becomes unavailable mid-build, or how capacity is realistically forecast at the Permit to Build gate.

Recommendation: Add a volunteer capacity plan as a required artifact at Gate 4.3. Define minimum availability thresholds and contingency when key volunteers become unavailable.
GAP O No emergency / event-driven fast path

§12 allows exceptions "approved by ITC" with no criteria or timeline. Festival and event deadlines are immovable and real. Without a defined compressed path, urgent work will simply bypass the policy — and once it happens once, it happens routinely.

Recommendation: Define a formal emergency path with specific criteria (e.g. immovable event deadline ≤30 days, Tier 1/2 scope, pre-documented risks). Allow gates 1–4 to be combined in a 48-hour review. Gates 4.4 (Rollout) and 4.5 (Close) still required.

High Priority

GAP C Support model genuinely unclear

§3 says operational business-side support sits with Departments; §4.4 says IT transitions to a "production support group" after hypercare. These aren't reconciled. Who handles L1 user questions? L2 functional configurations? L3 technical issues? What are the hypercare exit criteria and duration?

Recommendation: Define a 3-tier support model (L1/L2/L3) with owners for each tier, and specify hypercare duration and exit criteria in §4.4.
GAP D Gate 4.2 and 4.3 naming overlap

§4.1 grants approval to proceed to requirements. §4.2 is titled "Permit to Design, Estimate, and Plan" but its body describes requirements elicitation — then grants approval to proceed to design and planning. §4.3 then says IT produces the technical design (which §4.2 just authorized). The naming is effectively off by one.

Recommendation: Either rename §4.2 to "Permit to Define Requirements" or explicitly move design work into §4.3's pre-work description to match the naming.
GAP E P0 classification has no defined consequence

§8 explains how ITC decides P0, but not what P0 actually gets you. Does a P0 skip gates? Jump the queue? Get dedicated resources? If a P0 still walks all four gates at normal speed, the label is meaningless. Priority tiers below P0 (P1/P2/P3) and a published backlog view are also missing.

Recommendation: Define what P0 designation means operationally (dedicated resources, expedited gate reviews, senior sponsor assignment) and create a published priority tier model (P0–P3).
GAP L No benefits realization / Gate 4.5 missing

§7 requires business value and expected benefits at intake, but nothing ever checks whether they materialized. The feedback loop that makes future estimates better doesn't exist.

Recommendation: Add Gate 4.5 "Permit to Close" — a post-implementation review at 60–90 days, reported to ITC, checking actual vs. promised benefits before formally closing the project record.
GAP Q No RACI table

A gate-by-gate RACI table would resolve several ambiguities at once — particularly the IT vs. Department support question and who approves rollout.

Recommendation: Append a RACI matrix as Appendix A covering all five gates and post-launch support.
GAP R Gate 4.4 rollout approval inconsistent with gates 4.1–4.3

ITC approves gates 4.1–4.3; §4.4 says rollout readiness comes jointly from IT RGC and the Department, with ITC absent. Deliberate or an oversight? This creates ambiguity about who has final authority for production deployment.

Recommendation: State explicitly whether ITC sign-off is required at Gate 4.4 or whether IT RGC + Department approval is intentionally the final authority for rollout.

Medium Priority

GAP F 5% variance rule under-specified

5% of which baseline — original or most recently re-approved? Cumulative or per change? 5% of a 12-month project is 18 days — very tight. Needs to be merged with the cost-cap idea (Satyanishth's comment), not stacked.

Fix: cost threshold = greater of 5% or a fixed dollar floor, tracked cumulatively; looser separate threshold for schedule.
GAP G Contingency not governed

Who owns the contingency budget? Is it drawn down with approval or automatically available? Does consuming contingency count toward the 5% change threshold? A project could burn 40% contingency with no change request at all.

Fix: Contingency requires ITC notification when consumed beyond a threshold; tracked against change request rules.
GAP H No ITC charter details

Composition, quorum, how decisions are made (consensus or vote), delegation when members are unavailable, and conflict-of-interest handling are all undefined for the body that holds sole discretion over prioritization and P0.

GAP I No Department appeal path

§8 gives ITC sole discretion; §10 gives ITC broad authority. There is no route for a Department that disagrees with an ITC decision. Add a defined escalation to BAPS Inc. leadership with criteria.

GAP J Vendor / third-party procurement absent

Many projects will be SaaS or vendor-delivered. No gate covers vendor selection, contract/licensing review, data processing terms, security assessment, or data-portability on exit.

Fix: Add vendor checklist to §4.2 assessment list and a vendor clause to §3.
GAP K Funding source never addressed

Department budget or central IT budget? What happens when an approved project crosses a fiscal-year boundary or exceeds available funds? §11 gives ITC "review of budgets" but no funding model sits underneath it.

GAP M Data governance thin

Beyond adding data terms, donor/devotee PII handling, retention policy, and cross-border data handling need at least a sentence — the reviewers span Melbourne, Chicago, and Houston.

GAP P Missing artifacts / templates not attached

The memo references but doesn't attach: project questionnaire, proposal template, change request form, PTX approval record, UAT sign-off, and rollout readiness checklist.

Fix: List as appendices with named owners and effective dates.
GAP S No metrics or policy review cadence

No KPIs defined (gate cycle time, estimate accuracy, change request volume, % delivered to approved cost). No commitment to reviewing the policy itself annually.
